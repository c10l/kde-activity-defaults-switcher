# 07: KCM string translation (i18n)

Type: grilling
Status: resolved
Blocked by: 03, 05

## Question

How are the KCM's strings translated, and against which catalog?

- The KCM runs inside System Settings, whose process-wide translation domain is System Settings' own — so how do QML `i18n()` and the C++ backend's strings resolve to the KCM's own catalog?
- What is the catalog/domain name, and how is it pinned against the `kcmutils_add_qml_kcm` target and the plugin JSON?
- Which strings live in QML vs the C++ backend (`ads-kcm`), and does `ads-domain` stay i18n-free?
- What build wiring (`find_package`, `ki18n_install`, po layout) and extraction (`Messages.sh`) are needed?

References: ticket 07 ACs (KCM UI strings), [01](01-kcm-build-wiring-and-kquickconfigmodule-lifecycle.md), [03](03-cpp-backend-boundary.md), [05](05-picker-inherit-entry-and-clear.md); KCMUtils source (`kquickconfigmodule.cpp`, `sharedqmlengine.cpp`), `klocalizedstring.h`, `klocalizedqmlcontext.h`, `KF6I18nMacros.cmake`, kcmutils `CMakeLists.txt`/`src/Messages.sh`, and the installed `kcm_screenlocker` KCM.

## Answer

Five decisions, grounded in the KCMUtils/ki18n sources:

**1. Translation domain = the KCM's plugin id; the catalog is named the same.** `KQuickConfigModule` already sets the QML engine's i18n domain to `metaData().pluginId()` (`kquickconfigmodule.cpp`: `d->engine->setTranslationDomain(componentName)` with `componentName = metaData().pluginId()`, via a `KLocalizedQmlContext` installed as the QML context object in `sharedqmlengine.cpp`). So QML `i18n()`/`i18nc()` resolve against the KCM's own catalog with no per-call domain. The plugin id is the plugin JSON basename, which is the `kcmutils_add_qml_kcm` target name; pin it to `activity-defaults-switcher-kcm`, giving the catalog/domain `activity-defaults-switcher-kcm`. (The daemon's id was originally the parallel `activity-defaults-switcher-kded`; ticket 26 renamed it to the D-Bus-safe `kde_activity_defaults_switcher`, because kded6 uses the id as a D-Bus object-path element. The KCM id keeps its hyphens: a KCM id is not used on D-Bus, only as the catalog/domain name.) The implementer may rename as long as the JSON basename, the target, and the catalog stay in sync.

**2. C++ backend strings use the same domain explicitly.** The C++ side (`ads-kcm`) runs in System Settings' process, so the process-wide domain is System Settings', not ours. Its strings must therefore use the domain variants — `i18nd(domain, …)`, `i18ndc(domain, context, …)` — with a single `kcmTranslationDomain` constant (`"activity-defaults-switcher-kcm"`), never bare `i18n()`. QML keeps using bare `i18n()`/`i18nc()` (optionally the `KI18n.*`-prefixed form via `import org.kde.ki18n`, which `klocalizedqmlcontext.h` recommends for qmlls/qmllint friendliness).

**3. String placement: QML draws; C++ supplies only its own labels.** QML strings ("No activities to configure", "Reset", section headings) live in `ui/*.qml` with `i18n()`. The C++ translatable strings are the component display names (the model's name role) and the Inherit labels ("Inherit", "Inherit (baseline: %1)") — both composed in `ads-kcm` per tickets 03/05, using `i18ndc`/`i18nd`. `ads-domain` stays pure and i18n-free: it has no user-facing strings (`componentKey` is a config key, not a display name), so the daemon never gains a translation dependency. Component display names are a new `ads-kcm` function, not an `ads-domain` one.

**4. Build wiring.** `find_package(KF6I18n)` and link `KF6::I18n` into the KCM and `ads-kcm`; `ki18n_install(po)` compiles `po/<lang>/activity-defaults-switcher-kcm.po` → `.mo` and installs to `share/locale/<lang>/LC_MESSAGES/` (the location `KLocalizedString` searches). New build deps: `libkf6i18n-dev` (already present transitively via KConfig — declare it explicitly) and `gettext` (for `msgfmt`). `kdesdk-scripts` (for `extractrc`) is extraction-only, not a build dependency.

**5. Extraction.** A repo-root `Messages.sh` runs `$EXTRACTRC` over `.ui`/`.rc`/`.kcfg`, then `$XGETTEXT` over `.cpp`/`.h`/`.qml` into `activity-defaults-switcher-kcm.pot`. The plugin JSON's `Name`/`Description`/`X-KDE-Keywords` are translated through the same catalog (the l10n pipeline injects `Name[lang]` etc. into the JSON from it, and `kcmutils_generate_desktop_file` forwards whatever `Name*` keys are present). Extraction runs in the KDE translation pipeline (`extract-messages.sh`/Scripty), not in `make`; until `.po` files exist, the build installs nothing and shows only the English strings.
